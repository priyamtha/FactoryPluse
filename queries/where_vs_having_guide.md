# SQL Filtering Guide: WHERE vs. HAVING

This document defines the best practices for filtering data in SQL queries. It answers the fundamental engineering question: **How do we retrieve "Enterprise customers with >$10k annual spending" correctly and efficiently?**

---

## The Rule of Thumb

* Use **`WHERE`** to filter individual **rows** *before* grouping or aggregation.
* Use **`HAVING`** to filter aggregated **groups** *after* grouping has occurred.

### Case Study: Enterprise Customers with >$10k Annual Spending
To fetch this cohort, we combine both filtering methods because the criteria operate on different levels:
1. **`customer_type = 'Enterprise'`** is a row-level attribute of a customer. We filter this **before** grouping using `WHERE`.
2. **`annual_spending > 10000`** is an aggregated calculation (`SUM(amount)`). We must calculate this sum first by grouping, and then filter it **after** grouping using `HAVING`.

```sql
SELECT 
    t.customer_id, 
    SUM(t.amount) as annual_spending
FROM transactions t
JOIN customers c ON t.customer_id = c.customer_id
WHERE c.customer_type = 'Enterprise'  -- Row Filter: Selects only Enterprise rows first
GROUP BY t.customer_id
HAVING SUM(t.amount) > 10000;         -- Group Filter: Restricts groups to those exceeding 10k spend
```

## Detailed Comparison Table

| Aspect | `WHERE` Clause | `HAVING` Clause |
| :--- | :--- | :--- |
| **Execution Order** | Run **before** the `GROUP BY` clause. | Run **after** the `GROUP BY` and aggregation. |
| **Filter Level** | Filters raw rows of data. | Filters aggregated summary records. |
| **Supported Data** | Columns present in the source tables. | Aggregated functions (`SUM`, `AVG`, `COUNT`, `MIN`, `MAX`) and grouping columns. |
| **Join Interaction** | Can filter rows from joins before aggregates. | Filters joined groupings. |
| **Performance** | **High Efficiency**: Reduces row volume before CPU-heavy grouping operations. | **Moderate**: Must evaluate all groups generated by the `GROUP BY` clause. |

## Best Practices Checklist

### 1. Clean Data Early with `WHERE`
Always filter out cancelled orders, test transactions, refunds, and invalid date ranges inside `WHERE`. Do not carry unnecessary rows into the grouping stage.
* *Bad*: `GROUP BY customer_id HAVING transaction_status = 'completed'`
* *Good*: `WHERE transaction_status = 'completed' GROUP BY customer_id`

### 2. Never Use `HAVING` for Non-Aggregated Fields
If a column does not have an aggregate function applied to it (and is not one of the grouping columns), it should never appear in the `HAVING` clause.
* *Bad*: `GROUP BY customer_id HAVING customer_type = 'Enterprise'`
* *Good*: `WHERE customer_type = 'Enterprise' GROUP BY customer_id`

### 3. Minimize CPU Workload
By placing date ranges (e.g. `transaction_date >= DATE '2024-01-01'`) in the `WHERE` clause, SQL query planners can perform partition pruning or index scans, fetching only the required records and speeding up execution by orders of magnitude.
